== Resumen

Esta práctica conecta n8n con el sistema de la Práctica 5: PostgreSQL proporciona persistencia y RabbitMQ permite intercambiar eventos de forma asíncrona. Se configuran las credenciales de ambos servicios, se conecta n8n a la red de Docker Compose y se prueban los flujos de producción y consumo de mensajes, teniendo en cuenta que varios consumidores de una misma cola compiten por sus mensajes.

.Objetivos

* Integración de bases de datos relacionales.
* Comunicación asíncrona con colas de mensajes.
* Gestión de redes de contenedores.
* Orquestación de procesos de negocio.
* Diseño de flujos de trabajo asíncronos.

== Objetivos de la Práctica

En la práctica anterior, construimos un ecosistema de microservicios completo y funcional utilizando Docker Compose, con una API web, una base de datos PostgreSQL y un bróker de mensajes RabbitMQ. Sin embargo, este sistema existía de forma aislada. Esta práctica cierra el círculo, conectando nuestra instancia de n8n con dicho ecosistema.

El objetivo es posicionar a n8n como el "orquestador" o "pegamento" de alto nivel que consume y coordina estos microservicios. Aprenderemos a interactuar directamente con la base de datos PostgreSQL para persistir y consultar datos, y nos comunicaremos de forma asíncrona con RabbitMQ, tanto para enviar mensajes (producir) como para iniciar flujos de trabajo a partir de mensajes en una cola (consumir).

Al finalizar esta sesión, el estudiante habrá desarrollado las siguientes competencias:

* *Integración de Bases de Datos:* Configurar y utilizar el nodo `PostgreSQL` para realizar operaciones CRUD (Crear, Leer, Actualizar, Borrar) directamente contra la base de datos de un servicio externo.
* *Comunicación Asíncrona (Producción):* Implementar el nodo `RabbitMQ` (Send) para publicar mensajes en una cola, desacoplando la ejecución del flujo de trabajo de los servicios que procesarán dichos mensajes.
* *Comunicación Asíncrona (Consumo):* Diseñar flujos de trabajo reactivos que se inician automáticamente al recibir un mensaje, utilizando el `RabbitMQ Trigger`.
* *Gestión de Redes de Contenedores:* Comprender y solucionar los desafíos de red al conectar contenedores que se ejecutan en diferentes redes de Docker (la instancia de n8n y la pila de Docker Compose).
* *Orquestación de Procesos de Negocio:* Diseñar flujos de trabajo complejos que actúan como la lógica de negocio central, coordinando múltiples servicios (API, BBDD, colas de mensajes) para completar una tarea.

== Fundamentos Teóricos

=== Integración Directa con Bases de Datos: El Nodo `PostgreSQL`

//[.thumb]
//.Nodo PostgreSQL
//image::1.png[Nodo PostgreSQL, align=center, link=""]

Si bien Google Sheets (Práctica 3) es útil para prototipos y tareas sencillas, los sistemas de producción dependen de bases de datos relacionales como PostgreSQL para garantizar la integridad, concurrencia y escalabilidad de los datos. n8n proporciona un nodo `PostgreSQL` dedicado para estas integraciones.

Este nodo abstrae la complejidad de la conexión y permite realizar operaciones comunes:

* **Select:** Ejecuta una consulta `SELECT` y devuelve los resultados como un array de ítems JSON, listos para ser procesados por los siguientes nodos.
* **Insert:** Inserta uno o más ítems en una tabla especificada. n8n mapea automáticamente las claves JSON a las columnas de la tabla.
* **Update:** Actualiza filas existentes basándose en una condición.
* **Delete:** Elimina filas que coinciden con una condición.
* **Execute Query:** Ofrece control total, permitiendo ejecutar cualquier consulta SQL, incluyendo DDL (ej. `CREATE TABLE`) o consultas complejas con `JOINs`.

El pilar de esta integración es la **credencial de PostgreSQL**, donde se almacena de forma segura el host, puerto, usuario, contraseña y nombre de la base de datos.

=== Flujos Asíncronos: Nodos `RabbitMQ`

En la Práctica 5, introdujimos RabbitMQ para desacoplar nuestra API web del servicio de procesamiento. n8n puede participar en esta arquitectura asíncrona como productor, consumidor, o ambos.

* **`RabbitMQ` (Send) Node:** Este nodo actúa como un **productor**. Se conecta al bróker y publica un mensaje en una cola. Esto permite delegar tareas a un *worker* (por ejemplo, el de Python de la Práctica 5) sin que el flujo espere a que se complete su procesamiento.

* **`RabbitMQ Trigger` Node:** Este nodo es un **consumidor**. Mantiene una conexión con RabbitMQ y escucha mensajes en una cola. Al recibir uno, inicia una ejecución del flujo con el contenido del mensaje. Los consumidores que escuchan la *misma cola* compiten por los mensajes: cada mensaje se entrega a un consumidor, no se duplica automáticamente para todos. Para que varios servicios reciban el mismo evento se necesitan colas distintas enlazadas a un exchange de tipo `fanout` (fuera del alcance de este guion).

=== El Desafío de la Red: Conectando n8n a la Pila de Docker Compose

Este es el concepto teórico más crítico de esta práctica. Nuestra instancia de n8n (iniciada en la Práctica 1) se ejecuta en su propio contenedor Docker. La pila de microservicios de la Práctica 5 (web, db, mq, worker) se ejecuta en un conjunto separado de contenedores, gestionados por Docker Compose.

Por defecto, Docker Compose crea una red para la pila de servicios (por ejemplo, `task-manager-service_default`; el nombre exacto depende del directorio y de la versión de Compose). Dentro de esta red, los servicios pueden comunicarse usando sus nombres (por ejemplo, `web` con `db:5432`). Sin embargo, el contenedor de n8n queda fuera de esa red y no puede resolver `db` o `mq` hasta que se conecte a ella.

Hay dos alternativas de conexión. En ambos casos, PostgreSQL usa el protocolo PostgreSQL (no HTTP):

1.  **Acceso a través del host (desarrollo):** Si n8n se ejecuta en un contenedor separado, `localhost` apunta al propio contenedor de n8n, no al ordenador anfitrión. En Docker Desktop se puede usar `host.docker.internal` con los puertos publicados por Compose (`5433` para PostgreSQL y `5672` para RabbitMQ). En Linux puede ser necesario configurar explícitamente la puerta de enlace del host. Publicar puertos amplía la superficie de exposición; limítelos a `127.0.0.1` si solo se necesitan desde el host.

2.  **Conectar n8n a la red de Compose (opción recomendada para esta práctica):** Conecte el contenedor de n8n a la red de la pila. Así podrá usar `db:5432` y `mq:5672`, sin publicar esos puertos para n8n. Este procedimiento manual puede perderse si se elimina y recrea el contenedor de n8n; para despliegues persistentes, declare una red compartida en la configuración de ambos proyectos.

El comando para esto es:
`docker network connect <nombre_de_la_red_compose> <nombre_del_contenedor_n8n>`

Una vez que n8n está conectado a esa red, puede resolver los nombres de servicio `db` y `mq`. Use esos nombres como host en las credenciales y los puertos internos, no los puertos publicados al host.

== Desarrollo del Flujo de Trabajo Guiado

En este ejercicio, conectaremos n8n al sistema de la Práctica 5. n8n leerá datos de la base de datos PostgreSQL, y luego actuará como productor y consumidor de mensajes de RabbitMQ.

=== Paso 1: Preparar el Entorno de Microservicios

1.  Navegue al directorio `task-manager-service` de la Práctica 5.
2.  Inicie la pila de servicios completa en segundo plano:
    [source,bash]
    ----
    docker compose up -d --build
    ----
3.  Verifique que los cuatro contenedores (`task-manager-web`, `task-manager-worker`, `task-manager-db`, `task-manager-mq`) están en funcionamiento y saludables:
    [source,bash]
    ----
    docker compose ps
    ----

=== Paso 2: Conectar n8n a la Red de Microservicios

1.  Averigüe el nombre de la red creada por Docker Compose:
    [source,bash]
    ----
    docker network ls
    ----
    Busque la red del proyecto, normalmente `task-manager-service_default` (el separador puede variar según la versión de Compose).

2.  Averigüe el nombre de su contenedor de n8n (probablemente `n8n`, como se definió en la Práctica 1):
    [source,bash]
    ----
    docker ps
    ----
3.  Conecte el contenedor de n8n a la red:
    [source,bash]
    ----
    docker network connect <nombre_real_de_la_red> <nombre_real_del_contenedor_n8n>
    ----
    (Reemplace los nombres si los suyos son diferentes).
    No hay salida si el comando tiene éxito. Ahora n8n puede comunicarse con `db` y `mq`.

=== Paso 3: Configurar las Credenciales en n8n

1.  **Credencial de PostgreSQL:**
    * Vaya a "Credentials" en n8n y haga clic en "Add credential".
    * Busque `PostgreSQL`.
    * Use los siguientes valores (basados en el `docker-compose.yml` de la Práctica 5):
        * **Credential Name:** `PostgreSQL (Tasks)`
        * **Host:** `db`
        * **Database:** `taskdb`
        * **User:** `user`
        * **Password:** `password`
        * **Port:** `5432`
        * **SSL:** `false`
    * Guarde la credencial.

2.  **Credencial de RabbitMQ:**
    * Añada otra credencial y busque `RabbitMQ`.
    * Use los siguientes valores:
        * **Credential Name:** `RabbitMQ (Tasks)`
        * **Host:** `mq`
        * **User:** `task_user`
        * **Password:** `task_password`
        * **Port:** `5672`
        * **Virtual Host:** `/`
    * Guarde la credencial.

=== Paso 4: Flujo 1 - Interacción Directa con la Base de Datos

Vamos a crear un flujo que lee todas las tareas de la base de datos.

1.  Cree un nuevo flujo de trabajo. Comience con un `Manual Trigger`.
2.  Añada un nodo `PostgreSQL`.
3.  Configure el nodo:
    * **Credential:** `PostgreSQL (Tasks)`
    * **Operation:** `Select`
    * **Table:** `task` (este es el nombre de la tabla creada por `app.py` en P5).
4.  Ejecute el nodo (`Test step`). Debería ver una salida JSON con las tareas que haya creado previamente a través de la API (Práctica 5).
5.  (Opcional) Pruebe la inserción:
    * Cambie la **Operation** a `Insert`.
    * **Table:** `task`
    * En **Columns**, añada dos campos:
        * `title`: `Tarea creada desde n8n`
        * `description`: `Prueba de integración directa con BBDD`
    * Ejecute el nodo.
    * Vuelva a poner el nodo en modo `Select` y ejecútelo de nuevo. Debería ver su nueva tarea en la lista.

=== Paso 5: Flujo 2 - n8n como Productor y Consumidor (Asíncrono)

Crearemos dos flujos para demostrar el patrón asíncrono.

**Flujo A: El Productor (Webhook -> RabbitMQ)**

Este flujo recibirá una petición web y enviará la tarea a RabbitMQ.

1.  Cree un nuevo flujo de trabajo y nómbrelo "Productor de Tareas".
2.  Añada un `Webhook Trigger`.
3.  Para probarlo, pulse *Listen for test event* en el nodo y copie la *Test URL*. Esta URL solo está disponible mientras n8n está escuchando el evento de prueba. Para una ejecución activa, use la *Production URL* (ruta `/webhook/`, no `/webhook-test/`).
    Mantenga este webhook sin autenticación únicamente para la prueba local; si se expone fuera del equipo, configure autenticación en el nodo.
4.  Añada un nodo `RabbitMQ` (el de *acción*, no el *trigger*).
5.  Configure el nodo:
    * **Credential:** `RabbitMQ (Tasks)`
    * **Operation:** `Send a Message to RabbitMQ`.
    * **Queue:** `task_created` (la misma cola que el worker de P5 escucha).
    * En el parámetro **Message**, envíe el cuerpo como JSON. En el Webhook Trigger, el cuerpo suele estar en `{{ $json.body }}`; si el parámetro requiere texto, use `{{ JSON.stringify($json.body) }}`.
6.  Guarde el flujo. Para probar con la *Test URL*, deje abierto *Listen for test event*; para usar la *Production URL*, publique/active el flujo.
7.  Abra una terminal y use `curl` con la URL copiada del nodo:
    [source,bash]
    ----
    curl -X POST -H "Content-Type: application/json" \
         -d '{"title": "Tarea enviada por Webhook n8n", "description": "A cola RabbitMQ"}' \
         http://<host-accesible-de-n8n>:5678/webhook-test/<ruta-mostrada-en-el-nodo>
    ----
    Si usa la URL de producción, sustituya `/webhook-test/` por `/webhook/` y asegúrese de que el flujo esté activo.
8.  Mire los logs de Compose (ejecutando `docker compose logs -f worker`). El *worker de Python* de la Práctica 5 debería registrar `Tarea recibida: ID=None, Título='Tarea enviada por Webhook n8n'`. El mensaje enviado directamente a RabbitMQ no crea por sí mismo una fila en PostgreSQL.

**Flujo B: El Consumidor (RabbitMQ -> Log)**

Este flujo escuchará en la misma cola y registrará el mensaje.

1.  Cree un nuevo flujo de trabajo y nómbrelo "Consumidor de Tareas".
2.  Use un `RabbitMQ Trigger` como primer nodo.
3.  Configure el disparador:
    * **Credential:** `RabbitMQ (Tasks)`
    * **Queue:** `task_created`
4.  Conecte un nodo `Edit Fields (Set)` para simular un procesamiento.
    * **Name:** `procesado_por`
    * **Value:** `n8n_consumidor`
    * Active **Include Other Input Fields** para conservar el contenido del mensaje en la salida.
5.  Guarde y active este flujo.
6.  Para observar el consumo por n8n sin competencia, detenga temporalmente el worker de Python con `docker compose stop worker`.
7.  Active el flujo "Consumidor de Tareas" y envíe un mensaje nuevo con el `curl` del flujo A. Si vuelve a usar la *Test URL*, pulse antes *Listen for test event* otra vez; la URL de producción puede reutilizarse mientras el flujo esté activo.
8.  Vaya a "Executions" en n8n e inspeccione el mensaje recibido.
9.  Reinicie el worker con `docker compose start worker`. Si ambos consumidores están activos al mismo tiempo, cada mensaje lo recibirá solo uno de ellos; RabbitMQ no lo duplica.

== Ejercicios Propuestos

=== Ejercicio 1: Eliminación de Tareas (Dificultad: Baja)

*Objetivo:* Crear un flujo de trabajo que elimine una tarea de la base de datos PostgreSQL.
*Requisitos:*

1.  Cree un flujo que comience con un `Manual Trigger`.
2.  Añada un nodo `Edit Fields (Set)` para definir la ID de la tarea a eliminar (ej. `{"id_a_borrar": 1}`).
3.  Use un nodo `PostgreSQL` con la operación `Delete`.
4.  Configure la condición `WHERE` para que elimine la fila donde `id` sea igual a la expresión `{{ $json.id_a_borrar }}`.
5.  (Opcional) Añada otro nodo `PostgreSQL` (Select) al final para verificar que la tarea ha sido eliminada.

=== Ejercicio 2: Servicio de Notificación (Dificultad: Media)

*Objetivo:* Re-implementar el "Ejercicio 1" de la Práctica 5, pero usando n8n como el consumidor de la cola `task_completed`.
*Requisitos:*

1.  Modifique el flujo "Productor de Tareas" (o cree uno nuevo) para que llame al endpoint `PUT /tasks/<id>/complete` de la API web de la Práctica 5 (si no lo implementó, modifique este ejercicio para que su flujo simplemente envíe un mensaje a la cola `task_completed`).
2.  Cree un nuevo flujo en n8n que comience con un `RabbitMQ Trigger`.
3.  Configure este trigger para que escuche en la cola `task_completed`.
4.  Cuando reciba un mensaje, el flujo debe usar un nodo `Send Email` (o Slack, etc.) para notificar que la tarea ha sido completada, incluyendo el título de la tarea en el cuerpo del mensaje.
5.  En la implementación de referencia de P5, el worker de Python también escucha en `task_completed`. Deténgalo temporalmente (`docker compose stop worker`) o quite ese consumidor mientras prueba n8n; si ambos están activos competirán por los mensajes y cada mensaje se entregará a uno solo.

=== Ejercicio 3: Reemplazo de la API con Webhook (Dificultad: Alta)

*Objetivo:* Reemplazar completamente la lógica del endpoint `POST /tasks` de la API de Flask con un flujo de trabajo de n8n.
*Requisitos:*

1.  Cree un flujo con un `Webhook Trigger` configurado para `POST` y una ruta propia (por ejemplo, `tasks-from-n8n`). El cuerpo recibido tendrá `title` y `description`, accesibles normalmente como `{{ $json.body.title }}` y `{{ $json.body.description }}`.
2.  Valide que `title` sea una cadena no vacía. Para datos inválidos, devuelva una respuesta HTTP `400` mediante un nodo `Respond to Webhook`; `Stop and Error` detiene la ejecución con error, pero no genera por sí mismo una respuesta `400` controlada.
3.  En la rama válida, use un nodo `PostgreSQL` (`Insert`) para insertar en `task` las columnas `title` y `description`. Compruebe que el resultado del nodo incluye la fila insertada y su `id`; si usa una consulta, utilice `INSERT ... RETURNING id, title, description, done` y parámetros en vez de concatenar valores en SQL.
4.  Use un nodo `RabbitMQ` para publicar la fila insertada como JSON en `task_created`. El mensaje debe conservar los campos superiores `id`, `title`, `description` y `done`, ya que el worker de P5 espera `title` en el objeto raíz.
5.  En el Webhook seleccione la respuesta *Using 'Respond to Webhook' Node*. Conecte un nodo `Respond to Webhook` después de la inserción y la publicación; devuelva la tarea creada y el código HTTP `201`. No seleccione *Immediately*, porque esa opción solo devuelve `Workflow got started` sin esperar los datos.
6.  Pruebe el endpoint con la *Test URL* mientras el nodo está en *Listen for test event*. Para uso normal, active el flujo y llame a la *Production URL* (`/webhook/...`).

== Conclusiones y Avance de la Próxima Práctica

En esta práctica, hemos unificado nuestro ecosistema de microservicios con n8n, demostrando cómo puede actuar como el "pegamento" central de la lógica de negocio. Hemos interactuado directamente con una base de datos PostgreSQL y hemos participado en una arquitectura de comunicación asíncrona con RabbitMQ. n8n ha pasado de ser una herramienta aislada a ser el orquestador principal de un sistema distribuido.

Hemos dominado la lógica basada en reglas (IF, Switch) y la integración de servicios estructurados (APIs, BBDD, Colas). En la próxima práctica, daremos el salto final hacia la lógica moderna basada en modelos.

En la próxima práctica, exploraremos:

* **Uso y Personalización de Modelos de IA:** Introduciremos la integración de modelos de Inteligencia Artificial Generativa en nuestros flujos.
* **Integración con Modelos Gemini:** Nos centraremos en cómo n8n puede conectarse y orquestar los modelos **Gemini** de Google para realizar tareas avanzadas.
* **Orquestación de Flujos de IA:** Construiremos flujos de trabajo que utilicen IA para tareas como clasificar el sentimiento de las entradas de los clientes, generar resúmenes automáticos para las tareas en nuestra base de datos PostgreSQL, o crear contenido de forma dinámica.
